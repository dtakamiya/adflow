# 並列エージェント実行スキル

## 鉄則（絶対ルール）

1. **依存関係のあるタスクを並列実行しない** — タスクAの出力がタスクBの入力になる場合、それは順次実行する。
2. **共有リソースを競合させない** — 同じファイルを複数のエージェントが同時に編集することは禁止。
3. **各エージェントのスコープを明確に限定する** — 「全体を見て対応して」は禁止。具体的なファイル・関数・テストケースを指定する。
4. **統合後に必ずフルテストを実行する** — 個別に成功しても、統合時にコンフリクトやリグレッションが発生する可能性がある。

## Red Flags — よくある合理化

| 思考 | 現実 |
|------|------|
| 「全部まとめて並列に投げよう」 | タスク間の依存関係を分析してから判断する |
| 「同じファイルだけど別の関数だから大丈夫」 | ファイルレベルでのコンフリクトリスクがある |
| 「各エージェントが成功したから統合もOK」 | 統合テストは別途必要 |
| 「スコープを広げた方が柔軟に対応できる」 | スコープが広いと相互干渉のリスクが増大する |

## ワークフロー

### Step 1: タスクの分析と独立性の確認

並列実行の前に、タスク間の関係を分析する:

1. **タスクの列挙**: 実行すべきタスクを全てリストアップする
2. **依存関係の特定**: タスク間に入力/出力の依存があるか確認する
3. **共有リソースの特定**: 同じファイル・モジュール・テーブルを操作するタスクがないか確認する
4. **並列グループの決定**: 独立したタスクをグループ化する

**判定基準:**

| 条件 | 判定 |
|------|------|
| タスクが完全に独立（異なるファイル/モジュール） | 並列実行可能 |
| 同じファイルの異なるセクションを変更 | 順次実行を推奨（コンフリクトリスク） |
| タスクAの出力がタスクBの入力 | 順次実行必須 |
| 2タスク以下 | 並列化のオーバーヘッドが勝つため順次実行を推奨 |

### Step 2: エージェントへの委任

各タスクに対して、以下の情報をサブエージェントに提供する:

```markdown
## タスク: {タスク名}

### スコープ
- 対象ファイル: {具体的なファイルパス}
- 対象関数/クラス: {具体的な名前}

### 目標
{何を達成するか — 具体的に}

### 成功基準
- [ ] {テストが通る / エラーが解消される / 仕様通りに動作する}

### 制約
- {変更してはいけないファイル/関数}
- {守るべき設計方針}

### コンテキスト
{必要な背景情報 — ADR、仕様書、関連コードへの参照}
```

### Step 3: モデル選択ガイドライン

タスクの複雑さに応じてモデルを選択する:

| タスクの性質 | 推奨モデル | 例 |
|------------|-----------|-----|
| 機械的な修正・パターン適用 | Haiku | import文の修正、型注釈の追加 |
| 標準的な実装・テスト修正 | Sonnet | テストケースの修正、バグ修正 |
| アーキテクチャ判断を含む修正 | Opus | インターフェース設計、複雑なリファクタリング |

### Step 4: 結果の統合

全エージェントの完了後:

1. **結果サマリーの確認**: 各エージェントの成功/失敗を確認する
2. **コードコンフリクトの確認**: `git diff` で変更が競合していないか確認する
3. **フルテストスイートの実行**: 統合後に全テストを実行する
4. **スポットチェック**: 各エージェントの変更が意図通りか目視確認する

### Step 5: 完了報告

```markdown
# 並列実行結果

| タスク | エージェント | 結果 | 詳細 |
|-------|------------|------|------|
| {名前} | {モデル} | 成功/失敗 | {概要} |
| {名前} | {モデル} | 成功/失敗 | {概要} |

## 統合テスト結果
- テストスイート: PASS / FAIL ({passed}/{total})
- コンフリクト: なし / あり（{詳細}）

**総合判定**: 完了 / 要対応
```

## 適用シーン

### 良い適用例
- 3つ以上の異なるサブシステムのテスト修正
- 複数の独立したAPIエンドポイントの実装
- 異なるモジュールのリファクタリング
- 複数ファイルのコーディング規約適用

### 不適切な適用例
- 1つのバグの調査（→ `/systematic-debugging` を使用）
- 依存チェーンのある実装（→ `/stack-loop` で順次実行）
- 設計判断が必要な作業（→ `/adr` で先に方針を決定）

## stack-loop との連携

`/stack-loop` の実装計画で独立したタスクが複数ある場合、このスキルを組み合わせて効率化できる:

1. 実装計画からタスクの依存関係を分析する
2. 独立したタスクを並列グループに分類する
3. 各グループをサブエージェントに委任する
4. 統合後に verification-before-completion で検証する
