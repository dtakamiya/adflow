# 仕様書作成スキル

## アクティブなワークフロー（spec待ち）
!`ls docs/*/.adflow-context.md 2>/dev/null`

## 利用可能なADR一覧
!`ls docs/*/*-adr.md 2>/dev/null`

## 既存仕様書一覧
!`ls docs/*/*-spec.md 2>/dev/null`

## 鉄則（絶対ルール）

1. **ADRの決定事項に反する設計をしない** — 仕様書はADRの決定を具体化するもの。ADRと矛盾する設計を発見したら、仕様書ではなくADRの見直しを提案する。
2. **Mermaid図なしで仕様書を完成としない** — コンポーネント図・シーケンス図・ER図は必須。図なしの仕様書は仕様書ではない。
3. **プロジェクトのドメインに必要な設計セクションを省略しない** — 「該当なし」の場合もその理由を明記する。
4. **既存コードベースのパターンを無視しない** — 新しい設計は既存のアーキテクチャパターンに合わせる。

## Red Flags — よくある合理化

| 思考 | 現実 |
|------|------|
| 「図は後で描こう」 | 図なしの仕様書は実装者に誤解を与える |
| 「ADRの決定と少し違うが大丈夫」 | ADRとの乖離は設計破綻の始まり |
| 「設計の詳細は実装時に考えよう」 | 実装時では遅い。設計段階で決める |
| 「既存コードは参考にしなくていい」 | 既存パターンを無視すると保守性が崩壊する |
| 「エラーケースは主要なものだけでいい」 | 想定外のエラーが障害の原因になる |

## 引数の処理

- `$ARGUMENTS` が提供された場合:
  - ADR番号の場合: `docs/{番号}-*/01-adr.md` で検索し、該当する機能名ディレクトリを特定
  - 機能名の場合: `docs/{機能名}/.adflow-context.md` を直接読み込む
- `$ARGUMENTS` が空の場合: 以下の自動検出ロジックを実行する

### 前段ドキュメント自動検出

1. `docs/*/` 配下の `.adflow-context.md` をスキャンする
2. 「現在のステージ」が `spec` のコンテキストファイルを検索する
3. 該当が1件: そのワークフローのADRを自動選択する
4. 該当が複数: 一覧を提示してユーザーに選択してもらう
5. 該当なし: 旧方式のフォールバック（`docs/*-adr.md` から最新を候補提示 or `/adr` の実行を提案）

## 前提条件

- 関連するADRが `docs/{feature-name}/01-adr.md` に存在すること
- ADRが「承認済」ステータスであること（推奨）

## ワークフロー

### Step 1: ADR読込と分析

1. コンテキストファイルからADRのファイルパスを取得する
2. ADRファイルを **Read ツールで全文読み込む**
3. ADRから以下を抽出し、設計の入力コンテキストとして保持する:
   - **決定内容**: 選択された方式とその理由
   - **制約条件**: 技術的・ビジネス的制約
   - **追加考慮事項**: ADRに記載されたドメイン固有の考慮事項
4. 設計書のすべてのセクションで、ADRコンテキストとの **一貫性を維持する**

**エラーハンドリング:**
- 指定ADRが存在しない場合、利用可能なADR一覧を提示して選択を求める
- ADRが1つもない場合、`/adr` の実行を提案する

### Step 2: 既存コードベースの分析

1. プロジェクトの既存構造をスキャンする:
   - パッケージ構成
   - 既存のエンティティ・リポジトリ・サービス
   - 既存のAPIエンドポイント
2. 既存の設計パターンに合わせた設計を行う

### Step 3: コンポーネント設計

`templates/system-design-template.md` を使用して以下を設計:

1. **コンポーネント図**（Mermaid）: プロジェクトのアーキテクチャに基づく
2. **各コンポーネントの責務**

**エラーハンドリング:**
- テンプレートが見つからない場合、ユーザーに報告しビルトイン構造で代替する

### Step 4: シーケンス設計

1. **正常系シーケンス図**（Mermaid）: 主要フローを図示
2. **異常系シーケンス図**: 主要なエラーケース

### Step 5: API設計

1. エンドポイント一覧
2. リクエスト/レスポンスの JSON仕様
3. エラーレスポンスの標準化

### Step 6: データモデル設計

1. **ER図**（Mermaid）
2. **テーブル定義**: カラム名、型、制約
3. **インデックス設計**

### Step 7: ドメイン固有設計（プロジェクトに応じて）

ADRの考慮事項セクションと `references/` 配下のリファレンスに基づいて、プロジェクトのドメインに必要な設計セクションを追加する。例:
1. **エラーハンドリング**: エラー分類、リトライ可否
2. **非機能要件**: パフォーマンス、セキュリティ

**リファレンスが存在する場合**は積極的に参照し、設計に反映する。

### Step 8: 仕様書生成

1. `docs/{feature-name}/02-spec.md` にファイルを作成する
2. すべてのMermaid図が正しくレンダリングされることを確認する

**エラーハンドリング:**
- `docs/{feature-name}/` が存在しない場合は `mkdir -p docs/{feature-name}` で作成する

### Step 9: AI自己レビュー（自動品質チェック）

生成した仕様書に対して、AI自身で以下の品質を独自検証する:
- [ ] 必要なMermaid図（コンポーネント、シーケンス、ERなど）がすべて含まれているか
- [ ] API仕様のリクエスト/レスポンス形式が明確か
- [ ] エラーケースの定義漏れがないか
- [ ] ADRの決定事項に反していないか
- [ ] プロジェクトの既存パターンと整合しているか

問題があれば、ユーザーに提示する前に自律的に修正を行う。

### Step 10: 承認ゲート（HARD-GATE — 人間によるバリデーション）

自己レビューで品質を満たした仕様書をユーザーに提示する。

**ゲート条件チェックリスト:**
- [ ] Mermaid図（コンポーネント・シーケンス・ER）がすべて含まれている
- [ ] API仕様のリクエスト/レスポンスが定義されている
- [ ] ADRの決定事項との整合性が確認済み
- [ ] AI自己レビューの全項目がパス

**ユーザーアクション:**
- 「承認」→ Step 11 に進む
- 「修正」→ 指摘箇所を修正して再提示
- 「スキップ」→ ⚠️ **警告: 仕様書の承認をスキップすると、実装計画の品質が保証できません。本当にスキップしますか？**

### Step 11: コンテキスト更新

1. `docs/{feature-name}/.adflow-context.md` を更新する
2. 仕様書の成果物を記録: ファイルパス `docs/{feature-name}/02-spec.md`、ステータス「完了」
3. 現在のステージを `stack-plan` に更新する
4. ユーザーに案内する: **「次のステージ `/stack-plan` を実行するか、`/clear` して後で再開できます」**
   - **重要**: `/workflow` からの実行でない限り、自律的に次のコマンドを実行してはいけません。必ずユーザーからの明示的なコマンド実行（または進行の承認）を待ってください。

## リファレンス参照

設計時に `references/` ディレクトリ配下のリファレンスが存在する場合は参照する。リファレンスはプロジェクトのドメインに応じたパターン集であり、設計品質の向上に活用する。
