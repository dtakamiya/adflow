# 体系的デバッグスキル

## ビルドシステム
!`ls build.gradle build.gradle.kts pom.xml package.json pyproject.toml setup.py Cargo.toml go.mod Makefile *.csproj *.sln 2>/dev/null`

## 鉄則（絶対ルール）

1. **根本原因を調査せずに修正しない** — 場当たり的なパッチは問題を隠蔽し、新たなバグを生む。まず原因を特定する。
2. **一度に複数の変更をしない** — 1つの仮説につき1つの変更。複数同時に変更すると、何が効いたか分からなくなる。
3. **テストなしで修正を完了としない** — 修正には必ず再現テストを書く。テストが通って初めて修正完了。
4. **3回修正を試みて失敗したらエスカレーション** — 3回の修正が失敗した場合、単純なバグではなくアーキテクチャの問題を疑う。ユーザーに設計レベルの議論を提案する。

## Red Flags — よくある合理化

| 思考 | 現実 |
|------|------|
| 「とりあえずこの値を変えてみよう」 | 原因不明のまま値を変えるのはデバッグではない |
| 「一時的な回避策を入れておこう」 | 一時的な回避策は永遠に残る |
| 「他の部分は関係ないはず」 | 推測ではなくエビデンスで確認する |
| 「前は動いてたから最近の変更が原因だ」 | 最近の変更を確認するのは良いが、それだけに固執しない |
| 「ログを増やせば分かるだろう」 | ログは手段。まず仮説を立ててから必要なログを追加する |

## 引数の処理

- `$ARGUMENTS` が提供された場合: バグの概要として使用し、Phase 1 から開始する
- `$ARGUMENTS` が空の場合: ユーザーにバグの症状・再現手順を確認してから開始する

## ワークフロー

### Phase 1: 根本原因の調査（Investigation）

**目的**: 問題の正確な理解と再現条件の確立

1. **エラーの正確な把握**:
   - エラーメッセージ、スタックトレース、ログを収集する
   - 「いつから」「どの条件で」「どの頻度で」発生するかを確認する
2. **再現手順の確立**:
   - 最小限の再現手順を特定する
   - 可能であれば自動化された再現テストを書く（この時点では失敗するテスト）
3. **最近の変更の確認**:
   - `git log --oneline -20` で最近のコミットを確認する
   - `git bisect` の使用を検討する（明確な正常時点がある場合）
4. **コンポーネント境界の調査**:
   - 問題が発生するレイヤー（UI / API / DB / 外部サービス等）を特定する
   - 各境界での入力/出力を確認する

**Phase 1 の完了条件**: 問題の再現手順が確立され、発生箇所が特定されていること。

### Phase 2: パターン分析（Pattern Analysis）

**目的**: 正常なコードとの比較による差異の特定

1. **動作しているコードとの比較**:
   - 同じコードベース内の類似機能で正常に動作している箇所を見つける
   - 差分を系統的にリストアップする
2. **参照実装の完全な読解**:
   - スキミングではなく、関連コードを**完全に読む**
   - データフロー（入力→処理→出力）を追跡する
3. **差異のカテゴリ分類**:
   - 設定の差異
   - ロジックの差異
   - データ構造の差異
   - タイミング/順序の差異

**Phase 2 の完了条件**: 正常コードと問題コードの具体的な差異リストが作成されていること。

### Phase 3: 仮説と検証（Hypothesis & Testing）

**目的**: 根本原因の特定と検証

1. **仮説の明文化**:
   - 「{X}が原因で{Y}が発生している。なぜなら{Z}だから。」の形式で仮説を書く
   - 仮説が正しい場合に予測される挙動を記述する
2. **最小限の変更で検証**:
   - 一度に1つの変数だけを変更する
   - 変更前後の結果を比較する
3. **仮説が棄却された場合**:
   - 結果を記録し、次の仮説に移る
   - 棄却された仮説も記録として残す（同じ道を2度通らないため）

**Phase 3 の完了条件**: 根本原因が特定され、検証によって確認されていること。

### Phase 4: 修正の実装（Implementation）

**目的**: 根本原因に対する正しい修正

1. **失敗するテストケースの作成**:
   - バグを再現するテストを作成する（RED）
   - テストが確実に失敗することを確認する
2. **最小限の修正の実装**:
   - 根本原因のみを修正する（関連コードのリファクタリングは別途行う）
   - 修正を実装してテストが通ることを確認する（GREEN）
3. **リグレッション確認**:
   - 既存テストスイートを全て実行し、リグレッションがないことを確認する
   - 修正に関連するエッジケースのテストを追加する
4. **差分レビュー**:
   - `git diff` で変更内容を確認する
   - 修正が根本原因のみに対処しており、スコープが適切であることを確認する

**Phase 4 の完了条件**: テストが通り、リグレッションがなく、差分が根本原因の修正に限定されていること。

## エスカレーション条件

| 状況 | 対応 |
|------|------|
| 3回の修正試行が失敗 | ループ停止。アーキテクチャレベルの問題を疑い、ユーザーに設計議論を提案 |
| 再現手順が確立できない | ループ停止。追加情報（ログ、環境情報等）の収集をユーザーに依頼 |
| 修正範囲が3ファイル以上に及ぶ | 注意喚起。修正がスコープ外に広がっていないか確認し、必要に応じてADR作成を提案 |
| 修正によるリグレッションが発生 | 修正をリバートし、Phase 3 に戻って仮説を再検討 |

## 調査記録のフォーマット

デバッグセッション中は以下の形式で調査記録を維持する:

```markdown
# デバッグ記録: {問題の概要}

## 症状
- {エラーメッセージ / 異常な挙動}

## 再現手順
1. {手順}

## 調査した仮説

### 仮説 1: {仮説の内容}
- **検証方法**: {何をしたか}
- **結果**: 確認 / 棄却
- **根拠**: {エビデンス}

### 仮説 2: ...

## 根本原因
{特定された根本原因}

## 修正内容
{実施した修正の概要}
```
